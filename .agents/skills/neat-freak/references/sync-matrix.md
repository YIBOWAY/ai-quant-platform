# 变更影响矩阵

用这张表定位本次变更直接影响的说明；各行是按需检查位置，不要求每次读写全部位置。只有实施授权覆盖该文件时才修改；纯审查输出发现和拟议 diff。

## 代码事实到文档

| 代码变化 | 应同步的位置 |
|---|---|
| API 或路由 | 项目根路由表、用户/集成指南、架构说明 |
| 环境变量 | 项目根配置说明、runbook；下游需要配置时再进入接入指南 |
| 数据表或字段 | 架构数据模型、必要的项目根速查 |
| 用户流程 | README、用户指南、当前交接说明 |
| 部署或调度 | operator runbook、项目根启动说明、上下游所有权说明 |
| 跨进程协议 | 上游接口文档和下游消费文档 |
| 术语或命名 | 术语表及直接受影响的现役文档；历史原文保留，需要时补冻结提示 |

## 现役与历史

| 发现 | 处理 |
|---|---|
| 现役说明与代码冲突 | 直接改成当前事实 |
| 已被替代的计划、设计或验收快照 | 保留原文，加历史/冻结提示并指向现役文档 |
| 根指令里复制了长篇机制或变更流水 | 缩成稳定边界和权威文档指针 |
| 一次性事故细节 | 迁到 receipt/runbook；根指令只保留会防止重犯的规则 |
| 易变运行计数 | 绑定绝对时间和 generation/commit，或从稳定文档删除 |

## 能力文档的最小闭环

跨多文件的新能力通常需要四种视角；若已有权威文件，优先合并，不机械新增：

1. 用户或接入指南：怎么用、正常状态和错误。
2. 架构说明：数据流、状态与所有权。
3. Runbook：怎么验证、诊断和恢复。
4. Receipt/交接：哪次代码与运行证据证明了什么，哪些仍未验证。

## 跨项目检查

- 上游 API、共享配置、调度所有权或输出合同变化时，检查所有直接消费者。
- 对本次涉及的每个项目核对对应源码；只有结论涉及部署或运行态时才核对该目标。不要把一个仓库的 HEAD 当作另一仓库的事实。
- 文档同步不等于授权改代码、发布、推送或修改 agent 记忆。
