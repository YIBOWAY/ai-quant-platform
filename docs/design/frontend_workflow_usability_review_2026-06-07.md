# 前端使用问题定位与整改建议（2026-06-07）

> **状态（2026-06-15）**：本文为历史定位记录。其中大部分问题已在 2026-06-07 优化批次 #1/#2（见 [../frontend/optimization_log.md](../frontend/optimization_log.md)）与 2026-06-11 前端全面重构（见 [../delivery/frontend_refactor_2026-06-11_delivery.md](../delivery/frontend_refactor_2026-06-11_delivery.md)）中处理：因子实验室已默认 `futu` 真实数据且可切换；回测详情已有持久化基准曲线；回测已提供可选整股下单与最小订单金额约束；研报复现已有 `replication-*` run_id、文件落盘和详情页；期权雷达已有 `daily-task` 调度入口，会先刷新标的池、财报和 VIX 再扫描，并在页面显示最近一次调度任务状态；API 也已有显式开关控制的启动补跑，且周末启动会回退到上一个周五；模拟交易已拆分「实时账户 / 历史回放」双标签页；限价单已有基础 `pending_orders` 队列、页面挂单列表、手动检查入口和逐单取消；慢页已有 loading 状态。仍未处理：限价单资金/持仓预留、后台自动检查、停机补判、期权雷达完整交易所节假日判断和跨进程补跑锁。

## 1. 目标与范围

本文只做问题定位和方案建议，不包含功能代码改动。

覆盖范围：

1. 行情浏览的布局与打开速度。
2. 因子实验室的数据源、全零结果、结果解释和打开速度。
3. 回测详情的基准曲线、碎股订单，以及研报复现的 Top N 和结果入口。
4. 期权筛选器的结果区布局。
5. 期权雷达的自动刷新与自动扫描。
6. 模拟账户限价单的生命周期。
7. 策略再平衡的反馈和模拟交易页面布局。

## 2. 总体判断

这些问题不是单纯的“界面不好看”，而是三类问题叠加：

- **结果可信度问题**：因子实验室固定使用样例数据；回测详情缺少基准曲线；限价单的行为与用户理解不一致。
- **等待过程不可见**：页面在服务器取数、读取大文件或运行扫描时，用户点击后看不到即时反馈。
- **工作流组织不合理**：历史回放、持续账户、下单、再平衡和安全设置挤在同一页面；重要变化没有被直接展示。

### 推荐方案

建议采用“修正结果含义 + 后台预计算 + 工作区重排”的中等改造方案：

1. 先修正会误导判断的内容。
2. 再把耗时工作移到后台或缓存路径。
3. 最后重排页面，让用户先看到结果和变化，再看到操作表单。

不建议只加加载动画和缩小卡片。那样能缓解表面问题，但样例数据、基准缺失、限价单丢失和再平衡无反馈仍然存在。

## 4. 问题逐项定位与建议

## 4.1 行情浏览：图表下方空白过大，点击后无即时反馈

### 已确认原因

相关位置：

- `src/frontend/app/data-explorer/page.tsx`
- `src/frontend/components/CandlestickChart.tsx`
- `src/frontend/components/forms/DataExplorerControls.tsx`
- `src/frontend/lib/api.ts`

布局上，K 线所在区域会自动占满剩余高度，但 K 线图本身固定为 360 像素；原始行情表又固定占底部三分之一。屏幕较高时，多出来的高度就变成 K 线下方的大块空白。

打开页面时，服务器会同时读取标的列表和真实历史行情，并等待完成后才返回整页。当前没有该路由的加载占位，也没有侧边栏点击后的等待状态，因此用户会感觉“点了没反应”。

### 建议

1. 将中间区域改为明确的上下布局：
   - K 线区域使用可伸缩高度，图表跟随容器变高。
   - 原始行情表使用固定最小高度，并允许用户拖动分隔线调整高度。
2. 给行情浏览增加立即可见的加载状态：
   - 点击侧边栏后立刻显示页面骨架和“正在加载行情”。
   - 修改标的或日期后，旧图表保留并显示刷新状态，不清空整页。
3. 对历史行情做“先显示最近一次真实缓存，再后台刷新”。
4. 真实行情失败时显示错误或旧的真实缓存，不应静默切换成样例行情。

### 验收标准

- 高屏幕下，K 线与原始行情之间不出现大块空白。
- 点击行情浏览后 200 毫秒内出现明确反馈。
- 有缓存时先显示旧数据，刷新完成后再更新。
- 真实数据失败时不会被样例数据伪装成正常行情。

## 4.2 因子实验室：样例数据、全零结果、含义不清、打开结果慢

### 已确认原因

相关位置：

- `src/frontend/lib/api.ts`
- `src/frontend/app/factor-lab/page.tsx`
- `src/frontend/components/forms/FactorLabDashboard.tsx`
- `src/quant_system/api/routes/factors.py`
- `src/quant_system/factors/lab.py`
- `src/frontend/app/factor-lab/[runId]/page.tsx`

#### 数据源固定为样例数据

前端请求地址直接写死为：

`/api/factors/lab?provider=sample&universe_id=etf&symbol=QQQ&benchmark_symbol=QQQ`

因此页面显示 `SAMPLE / NOT REAL` 是当前代码的必然结果，不是数据源偶尔失效。

#### 全零不代表没跑

当前样例数据是高度规则化的趋势数据。实际复算结果：

- Momentum：z-score 始终为负，从未持仓，所以收益、胜率、交易数都是 0。
- MACD：同样始终未持仓，所以结果全为 0。
- RSI：样例数据中的 RSI 值恒定，滚动标准差为 0，无法产生有效 z-score，因此覆盖度为 0。
- Volatility 和 Liquidity：几乎始终持仓，只发生一次状态变化，产生了约 42 的异常高 Sharpe。

所以这些数字确实跑出来了，但没有研究参考价值。页面目前把“没有数据”“没有交易”“因子恒定”和“结果恰好为零”都显示成相同的 `0`，容易造成误解。

#### “打开结果”不是当前看板的详情

左侧的“最近保存结果”来自另一条因子运行记录，不是当前只读看板的缓存结果。按钮名称会让用户误以为它是当前 QQQ 择时诊断的详情。

详情接口会一次性返回数千条因子值、信号和相关记录。最新真实结果约 1.89 MB，页面只显示前几行，但仍要先下载全部内容，因此会等待数秒。

### 建议

1. 因子实验室只使用真实历史数据：
   - 默认使用 Futu。
   - Futu 不可用时使用最近一次真实缓存或 Tiingo。
   - 禁止自动回退到样例数据。
2. 将看板改为预计算结果：
   - 每个交易日收盘后或每周自动刷新。
   - 页面只读取最近一次成功结果，不在打开页面时重新计算。
3. 每个因子增加明确状态：
   - 有效。
   - 无交易信号。
   - 因子值恒定。
   - 数据不足。
   - 计算失败。
4. 不再用 `0` 代替无法计算的结果，使用 `--` 并显示原因。
5. 给每列增加直白解释，并增加一句结论，例如：
   - “该因子在这段时间从未触发持仓，不能据此评价收益表现。”
   - “该 Sharpe 来自几乎全程持仓且只切换一次，参考价值低。”
6. 将“打开结果”拆分为：
   - “查看本次看板详情”。
   - “查看最近保存的因子运行”。
7. 详情接口改为摘要优先、各表按需加载或分页加载。
8. 页面点击后立即显示加载骨架。

### 验收标准

- 页面默认数据源为真实数据，且明确显示数据截止日期。
- 不再把无法计算的结果显示为 0。
- 用户能直接理解每个指标和异常结果的原因。
- 打开看板在有缓存时不依赖现场计算。
- 打开详情时先显示摘要，大表随后按需加载。

## 4.3 回测：基准曲线缺失、碎股订单过多、研报复现入口不完整

### 4.3.1 基准曲线缺失

相关位置：

- `src/frontend/app/backtest/[runId]/page.tsx`
- `src/frontend/components/EquityComparisonChart.tsx`
- `src/quant_system/api/routes/benchmark.py`

详情页只读取并标准化策略曲线，没有读取基准曲线。图表组件已经支持基准曲线，基准接口也能正常返回数据，所以这是明确的页面缺陷。

### 建议

- 详情页根据本次回测保存的基准标的、日期和数据源读取基准曲线。
- 策略和基准按日期对齐后再绘图。
- 如果基准读取失败，保留策略曲线，并明确显示失败原因。

### 4.3.2 `BUY 0.0071 quantity` 等碎股订单

> **2026-06-15 后续状态**：回测表单和 `/api/backtests/run` 已提供 `min_order_value` 与 `whole_share_orders`。默认仍保持历史兼容（允许碎股、最小订单金额 0）；用户勾选整股模式后，订单生成与现金不足部分成交都会向下取整到整股。

相关位置：

- `src/quant_system/backtest/order_generation.py`
- `src/quant_system/backtest/models.py`
- `src/quant_system/backtest/broker.py`
- `src/frontend/components/forms/BacktestForm.tsx`

当前回测使用：

- 任意小数股。
- 每根 K 线再平衡。
- 精确追踪目标权重。
- 最小订单金额为 0。

只要权重与目标有几美元差异，就会生成小额订单。这不是计算错误，但会造成不现实的成交数量、过高换手和大量噪声订单。

### 建议

增加并默认启用更现实的交易约束：

1. 股票默认整股交易；允许用户明确选择是否支持碎股。
2. 增加最小订单金额，例如低于 100 或 500 美元不下单。
3. 增加再平衡容忍区间，例如权重偏差小于 1% 不交易。
4. 默认再平衡频率从“每根 K 线”改为每周或每月。
5. 结果页显示“因小额差异被忽略的订单数量”。

### 4.3.3 研报复现 Top N 应该填多少

相关位置：

- `src/quant_system/strategies/registry.py`
- `src/quant_system/api/routes/replications.py`
- `src/quant_system/replication/reversal_momentum.py`
- `src/frontend/components/forms/StrategyCatalogWorkbench.tsx`

当前规则：

- 留空：自动取每月可用标的数量的 10%，至少 1 个。
- 手动输入：允许 1-10。
- 每个月实际使用数量不会超过当月可用标的一半。

默认股票池只有 8 个标的，所以留空时实际通常是“做多 1 个、做空 1 个”。在这个默认股票池下，建议使用留空或填 1；如果填 3，结果会非常集中，且不再接近论文中的十分位组合。

更合理的界面应该直接显示：

- 当前股票池数量。
- 本次预计做多和做空各多少只。
- 留空代表“自动十分位”。
- 股票池过小时，提示这只是流程验证，不是严谨论文复现。

### 4.3.4 研报复现完成后没有“打开测试”

> **2026-06-15 后续状态**：已处理。`POST /api/replications/reversal-momentum/run` 会返回 `replication-*` `run_id`，写入 `data/api_runs/replications/<run_id>/metadata.json` 与 `result.json`；`GET /api/replications/reversal-momentum/{run_id}` 可重新读取，前端显示“打开复现”并跳转到 `/replications/{run_id}`。复现 run 暂不写入可选 PostgreSQL run index。

当时研报复现接口直接返回结果，但不会保存为一个可打开的运行记录，也不会返回 `run_id`。通用策略目录只有收到 `run_id` 才显示“打开回测”，因此按钮不会出现。

### 建议

- 将研报复现保存为独立的复现运行记录，并提供专门详情页。
- 运行完成后显示“打开复现详情”，不要叫“打开回测”。
- 复现详情应直接展示组合曲线、月度收益、持仓和论文诊断，而不是把结果压成键值表。

### 验收标准

- 回测详情始终显示策略与基准两条曲线，或明确说明基准失败原因。
- 默认设置不会产生大量几美元的噪声订单。
- Top N 输入旁能看到实际组合规模和建议。
- 研报复现完成后能打开专门详情页。

## 4.4 期权筛选器：结果摘要块过大

### 已确认原因

相关位置：

- `src/frontend/components/forms/OptionsScreenerForm.tsx`

结果区把每个数值都做成独立大卡片。部分卡片还带较长说明，导致同一行所有卡片被一起拉高。市场状态也单独占用一条大横幅，造成信息很少但占地很大。

### 建议布局

1. 市场状态改为顶部紧凑状态条，只显示状态、数据时间和影响。
2. 核心数字使用一行紧凑摘要：
   - 正股价格。
   - 到期日数量。
   - HV。
   - 候选数量。
   - 过滤数量。
3. EMA21、SMA50、HV/IV 判断改为两条状态行，不使用大卡片。
4. 详细解释放到提示图标或可展开区域。
5. 主要空间留给候选合约表和过滤原因。

### 验收标准

- 首屏能同时看到状态、核心数字和候选结果表开头。
- 摘要区不因某一项说明文字较长而整体变高。
- 过滤原因和候选结果比辅助指标更醒目。

## 4.5 期权雷达：改为自动刷新和自动扫描

### 已确认现状

相关位置：

- `src/frontend/components/forms/OptionsRadarView.tsx`
- `src/quant_system/api/routes/options_radar.py`
- `src/quant_system/options/data_refresh.py`
- `src/quant_system/options/radar.py`
- `src/quant_system/api/server.py`
- `scripts/run_options_radar.ps1`
- `docs/execution/phase_13_scheduler_setup.md`

当前界面提供手动刷新标的池、财报日历、VIX 和运行今日扫描。2026-06-15 起，已有计划任务脚本改为调用 `quant-system options daily-task`，会先刷新前三项再运行每日扫描，并写入 `daily_task_status.json`；页面会通过 `GET /api/options/daily-scan/status` 展示最近一次调度任务状态。设置 `QS_OPTIONS_RADAR_STARTUP_CATCHUP_ENABLED=true` 后，后端启动会在最近一个 UTC 工作日快照缺失时后台运行一次只读 `daily-scan` 补跑，周末回退到上一个周五。

扫描 100 个标的并读取期权链可能需要数分钟，且受 Futu 频率限制，不适合由用户打开页面后手动等待。

### 推荐自动任务

已增加统一的“雷达日终任务”，执行顺序：

1. 刷新标的池。
2. 刷新财报日历。
3. 刷新 VIX。
4. 运行期权雷达扫描。
5. 保存最新快照和任务状态。

运行时机建议：

- 每个美股交易日美东时间 16:15-16:30 运行，而不是正好 16:00，避免收盘数据尚未稳定。
- 后端启动时检查最近一次成功快照；当前已有 opt-in 启动补跑，并会在周末回退到上一个周五，后续应升级为完整交易所节假日判断。
- 不建议每次重启都无条件重复扫描，否则频繁重启会重复消耗数分钟并触发限频。

必须增加：

- 美东时区和夏令时处理。
- 完整美股交易所节假日判断（周末回退已完成）。
- 单实例锁，防止计划任务和启动补跑同时运行。
- 每一步的成功、失败和耗时记录（当前已有成功/失败状态记录，尚未记录耗时）。
- 失败时保留上一份成功快照。

### 页面调整

- 普通页面移除四个手动操作按钮。
- 页面顶部显示：
  - 最新成功扫描日期。
  - 数据截止时间。
- 最近一次调度任务完成/失败状态。
- 上次失败步骤。
- 手动重跑只保留在维护入口中，不放在日常使用界面。

### 验收标准

- 用户打开页面时直接看到最近一次成功结果。
- 交易日收盘后自动产生新快照。
- 部分满足：打开 `QS_OPTIONS_RADAR_STARTUP_CATCHUP_ENABLED=true` 后，项目启动会补最近一个 UTC 工作日缺失快照，周末会回退到上一个周五；仍未内置完整美股交易所节假日历。
- 自动任务失败不会删除上一份可用结果。

## 4.6 模拟交易：限价单应挂单等待

- `src/quant_system/execution/account_storage.py`

- `src/frontend/components/forms/AccountTradePanel.tsx`

当前撮合条件本身是正确的：

- 买入限价单：现价小于或等于限价时成交。
- 卖出限价单：现价大于或等于限价时成交。

历史问题在于每次提交订单都会临时创建一个撮合器，只检查一次当前价格。未满足价格条件时，订单被记录为“未成交”，随后临时撮合器被销毁，订单不再存在。

2026-06-15 起，基础持久挂单已落地：未触价的手动限价单返回 `pending`，写入 `PaperAccount.pending_orders`，账户页展示「待处理限价单」，可通过 `POST /api/paper/account/orders/process` / 页面「检查挂单」按当前真实纸面价格再次撮合，也可通过 `POST /api/paper/account/orders/{order_id}/cancel` / 行内「取消」移除挂单并写入 `order_cancelled` 账本事件。

### 建议

持久挂单能力的完成状态：

1. 已完成：模拟账户保存未触价的手动限价单。
2. 已完成：提交未触价限价单后返回 `pending`。
3. 已完成：页面展示未成交订单列表，并支持逐单取消。
4. 部分完成：可手动读取真实行情并触发成交；未完成：后台定期自动检查。
5. 未完成：买单预留购买力，卖单预留可卖数量，避免多个挂单重复占用同一资金或持仓。
6. 部分完成：重新检查只使用当前 `PaperPriceSource` 价格；未完成：更严格的新鲜度规则。
7. 未完成：明确后台停机期间的处理规则：
   - 简化方案：只在系统观察到满足价格时成交。
   - 更真实方案：启动后读取停机期间的日内高低价，判断是否曾触价。

推荐采用更真实方案，但应在页面明确说明模拟撮合规则。

### 验收标准

- 已满足：未满足价格的限价单显示为“挂单中”，不会消失。
- 已部分满足：满足价格后手动检查可成交并更新账户；后台自动成交未完成。
- 已满足：用户可以取消挂单。
- 未满足：多个挂单不会超用现金或超卖持仓。
- 已部分满足：页面能看到提交、挂单、取消和成交；预留、部分成交生命周期仍未完整展示。

## 4.7 策略再平衡：实际变化不可见，页面需要重排

### 已确认原因

相关位置：

- `src/frontend/app/paper-trading/page.tsx`
- `src/frontend/components/forms/AccountTradePanel.tsx`
- `src/quant_system/execution/account_service.py`
- `src/quant_system/api/routes/paper.py`

本次实际再平衡已经成功：

- 卖出 AAPL 100 股。
- 买入 QQQ 1418.319 股。
- 账户从 AAPL 持仓切换为 QQQ 持仓。

但页面摘要只显示净值、盈亏、现金和持仓数量。再平衡前后这四个数值分别仍是 100 万、0、0 和 1，因此用户看不出变化。

接口已经返回更新后的完整账户，但前端没有直接使用返回结果，只发起整页刷新。即使刷新成功，只要摘要数字不变，看起来仍像“没有反应”。

### 建议反馈方式

再平衡成功后立即显示一张“本次变化”回执：

- 卖出了什么。
- 买入了什么。
- 调整前后权重。
- 成交价格和数据时间。
- 是否有未完成或跳过的调整。

账户摘要旁应直接显示当前持仓前几名和权重，而不是只显示持仓数量。

### 建议页面布局

当前页面把持续账户、手动下单、策略再平衡、安全开关和历史回放全部堆在一个狭窄侧栏，并把历史回放结果放在主区域，日常账户操作反而不突出。

建议拆成三个工作区：

1. **账户**：账户摘要、当前持仓、未成交订单、最近成交和最近一次再平衡。
2. **交易与再平衡**：手动下单和策略再平衡，使用页内标签或侧边抽屉切换，不同时展开全部表单。
3. **历史回放**：独立标签或独立页面，避免与持续账户混淆。

安全开关保留在顶部明显位置，但使用紧凑状态条，不单独占用长侧栏。

### 验收标准

- 再平衡完成后立即显示前后变化，不需要用户自己判断摘要数字。
- 页面直接显示当前持仓标的和权重。
- 未成交订单和最近成交在账户首屏可见。
- 历史回放与持续账户明确分开。
- 常用操作不需要长距离向下滚动。

## 5. 方案选择

### 方案 A：只做表面修补

内容：

- 增加加载动画。
- 缩小卡片。
- 补上基准曲线。

优点：改动小、见效快。

缺点：样例因子结果、限价单预留/后台自动检查、雷达手动等待、再平衡无变化说明等核心问题仍然存在。

### 方案 B：修正行为并重排工作流（推荐）

内容：

- 真实数据和后台预计算。
- 结果状态与解释。
- 基准曲线和现实交易约束。
- 自动雷达任务。
- 持久限价挂单。
- 模拟账户页面重排。

优点：直接解决本次反馈中的核心问题，工作量可控，符合当前本地研究平台定位。

缺点：涉及前后端和持久化，需要分阶段实施。

### 方案 C：引入统一后台任务系统

内容：

- 所有耗时研究任务、扫描、因子刷新和挂单撮合都进入统一任务队列。
- 页面统一显示任务进度、结果和失败重试。

优点：长期架构最完整。

缺点：对当前规模偏重，容易扩大范围。本轮不建议直接采用。

## 6. 推荐实施顺序

### 第一阶段：修正会误导判断的问题

1. 回测详情补基准曲线。
2. 因子实验室切换为真实数据，并区分无数据、无信号和零结果。
3. 限价单改为基础持久挂单，不再显示为一次性失败；逐单取消已完成，预留/后台自动检查待做。
4. 再平衡增加前后变化回执。

### 第二阶段：消除等待无反馈

1. 为行情、因子详情和回测详情增加立即可见的加载状态。
2. 因子和回测详情改为摘要优先、明细按需加载。
3. 行情使用最近真实缓存并后台刷新。

### 第三阶段：自动化与页面重排

1. 为期权雷达补上完整交易所节假日判断和跨进程补跑锁；日终调度入口、页面任务状态、opt-in 启动补跑和周末回退已覆盖。
2. 重排模拟交易页面。
3. 压缩期权筛选器摘要区。
4. 调整行情浏览上下区域。

### 第四阶段：提升回测现实性

1. 整股或碎股模式。
2. 最小订单金额。
3. 再平衡容忍区间。
4. 更合理的默认再平衡频率。

## 7. 需要提前确定的产品取舍

实施前建议确认以下决定：

1. 因子实验室真实数据优先级：Futu 失败后使用 Tiingo，还是只显示上次真实缓存。
2. 限价单在后台停机期间是否需要根据日内高低价补判成交。
3. 股票回测默认采用整股，还是保留碎股但设置最小订单金额。
4. 期权雷达启动时严格每次重跑，还是只在最新快照过期时补跑。推荐后者。
5. 历史回放是保留在模拟交易页的独立标签，还是移动到独立页面。推荐独立页面。
