1总体结论

不需要整体重写。需要的是一次分阶段的定向治理。
8 个评估维度彼此独立工作，却得出了同一个结论：这个项目的正确性内核出乎意料地扎实——反前视（PIT）纪律经得起逐行审查、428 个后端测试 43 秒全绿、安全红线在核心代码里是真实存在的；真正让你“越用越不顺手”的，是边缘上的漂移与堆积：四套端口口径、算完即焚的结果、名实错位的页面、97% 是死重的存储目录、以及一个默认配置下永远成交不了的模拟回放。这些问题没有一个需要推倒重来，但它们叠加在每天的使用路径上，摩擦感就是你现在的体感。

2评估方法与可信度说明

本次评估通过多智能体工作流执行：8 个维度（后端架构、前端架构、UX 工作流、数据与存储、测试质量、DevOps/DX、文档知识、安全边界）各由独立评审智能体基于真实代码与数据逐项核查；每条 critical/high 级发现再交给 2 个互相独立的“质疑者”智能体做对抗复核——它们的任务是设法推翻发现，而不是附和。最后由一个完整性批评智能体专门回答“这次评估漏了什么”（其产出见 §5）。共动用 58 个智能体。

对抗复核实质性地修正了结果，本报告如实标注：

  • 已确认 2-0 — 两票均核实证据属实。本报告绝大多数 high 级发现属于此类。
  • 有争议 — 复核确认问题存在但对严重度有异议（如实验页问题，一票认为应降为 medium）。
  • 已否决 — 复核推翻了原发现。前端维度原报“断网时渲染假 $1M 账户”被证伪：兜底常量从未被渲染，断网时显示“--”。已按否决处理，仅保留其残余的可维护性问题。
  • 未复核 — medium/low 级发现未做对抗复核，证据为单一评审者核查，置信度相对较低。

多处发现的细节在复核中被修正（例如 kill-switch 问题比原报更严重：即使改了环境变量，前端硬编码与未暴露的风险限额仍会拒掉每一笔订单；又如回测详情“并行拉基准”的原建议被判不可行，因为基准参数依赖详情响应本身）。正文均采用修正后的版本。

3“用着不顺手”的根因分析

你的原话是“越来越不顺手”。把日常摩擦逐一对回已确认的发现，它们不是泛泛的“体验不好”，每一条都有具体的代码级根因：

日常体感代码级根因详见
1每天启动要折腾一圈，端口还经常对不上 启动是 5 步手工仪式（OpenD 图形界面 → docker → conda+uvicorn → 前端+参数 → 环境变量）；端口存在四套口径：README/AGENTS 说 8765+3001，日常 shell 用 8700，启动脚本写 8765+3000，.env.local 里还躺着一个早已没有后端监听的 8800——它就是上次 14 个 E2E 全挂事故的元凶。裸跑 npm run dev 会命中 8800+3000 这个全错组合。 §4.6
2点开回测详情要干等好几秒 详情页在打开时现场重新计算基准曲线（2026-06-07 实测 4.5–6.3 秒），而基准本可以在回测落盘时持久化一次；更糟的是基准数据源若降级为合成样例，页面不读 benchmark.source 字段，无任何警告地把合成基准画在真实策略旁边。 §4.3 F4
3模拟回放跑完了，账户却什么都没发生 QS_KILL_SWITCH 默认开启 → 风险引擎拒绝每一笔订单 → 现存 3 个真实回放 run 全部 trade_count=0、净值原地踏步，却照常落盘并被索引为“成功”运行。对抗复核进一步发现：即使关掉环境变量也没用——前端硬编码 enable_kill_switch:true，且未暴露的默认风险限额（单笔上限 $20k、单仓 50%）也会拒掉每笔约 $100k 的订单。UI 发起的回放在任何配置下都不可能成交。 §4.8 ①
4研报复现的结果，一切换页面就没了 复现结果只存在于组件的 useState 里，切换策略即清空（StrategyCatalogWorkbench.tsx:226），后端也从不持久化复现运行——这是全平台唯一“算完即焚”的研究产物，与回测/因子/回放的逐 run 落盘形成断裂。 §4.3 F1
5页面的名字、网址和内容对不上号 /replications 实为策略目录，/order-book 实为 Polymarket 研究页，导航里“Docs”只指向单篇论文文档，Agent Studio 的 LLM 是 stub 但提示弱（页面 :124 已有 “LLM: stub” 状态徽章，只是不显眼）；顶栏与侧栏双导航并存、同一页面两个名字、铃铛图标点开是期权雷达。每次使用都在交“认知税”。 §4.3 F2/F8
6运行历史里混进来路不明的 run Playwright 的后端 webServer 没有任何环境变量隔离：读你真实的 .env（含 QS_DATABASE_ENABLED=true），E2E 把测试 run 直接写进真实 data/api_runs 与真实 Postgres 索引；phase10 冒烟用例从不清理。现有 106 个回测目录里用户 run 与测试残渣已不可区分。 §4.5 ①
7data/ 目录越来越大、越来越乱 153 个逐 run DuckDB 副本约 195MB（= api_runs 体积的 97%）从未被任何代码读取过，纯属每次运行的双写死重；futu 期权缓存 62MB / 403 份快照 100% 过期且永不清扫；50+ 个 phase/smoke 目录与日志、缓存、产物混居，没有任何生命周期管理。 §4.4
8跑大一点的回测，浏览器就卡住干等 POST /backtests/run 是同步处理：Tiingo 全量下载 + 逐 bar 引擎循环 + 双写落盘全部发生在一次 HTTP 请求内——无进度、无法取消、超时即全丢。且 Tiingo 数据每次回测都重新全量下载，没有本地缓存接通。 §5 缺口3
9想改点东西，心里没底会不会弄坏别处 回测与模拟执行的订单生成是两份复制后已漂移的代码（行为差异见 §4.2 ①）；前端 50 个手写类型没有任何契约校验，后端改个字段前端只会安静地渲染“--”；前端纯函数零单元测试。改动的安全网有结构性空洞。 §4.1/§4.2

结论：“不顺手”不是审美问题，是九条具体的工程债在使用路径上的叠加。其中 1、3、4、6 四条尤其伤害“研究平台”的核心价值——它们让你不能完全信任自己看到的结果。

重构后的页面层是好的；脆弱的是页面层之下的“合同”——类型靠手抄、文案双轨、巨石组件无测试兜底。

注册表模式与分层是对的；债务集中在“复制后各自演化”——订单逻辑、配置、持久化各有一处分叉。

6.1 Postgres 运行索引：移除还是加固？

数据维度的技术结论是“复杂度倒挂”（§4.4 ③）：文件扫描 13-15ms 已经够快，DB 没有承担任何独占职责。但你明确表达过“用现成的 Docker quantplatform-db”的偏好，且 UX 维度建议的 /api/runs/recent（修复仪表盘空活动流）正好适合建在它上面。

方案 A：移除索引层方案 B：保留并加固（与你既有偏好一致）
做法删 runs_repository/database 启动对账，运行列表纯走文件扫描冻结 KIND_DIRS 语义、连接池化、加 @pytest.mark.pg 真库测试、在其上建 /api/runs/recent
得少一个硬依赖（psycopg）、少一套对账逻辑、心智更简单仪表盘活动流有了天然数据源；未来雷达/请求日志入库有承载
失仪表盘活动流要另找实现（直接扫文件也可，稍慢）维护一层当前收益很薄的间接性

两案工作量相当（均 M）。如果你日常确实开着 Docker 且未来想把更多研究产物入库，B 合理；如果 Docker 只是“为了这个索引才开”，A 更诚实。

6.2 限价单语义：保持 IOC 还是做持久挂单？

短期修法（帮助文案 + toast 明示）无论如何都该做。中期是否实现持久挂单池（含资金预留、停机期间触价补判等，工作量 L），取决于你对模拟交易真实感的要求。若做，需要决定停机期间的触价规则（只认系统在线时见到的价格 / 启动后按日内高低价回溯补判）。

9渐进优化还是重构？—— 明确回答

你问“后续可以怎么更新优化，或者重构一下整个项目”。明确回答：渐进优化，不要重写。理由有三：

  1. 重写会丢掉最值钱的资产。这个项目最有价值的不是任何一个页面，而是 428 个回归测试（含“合成数据永不成交”“计划-提交中止”这类领域知识结晶）和经逐行验证的反前视纪律。重写它们必然在新代码里失传一段时间——而那段时间里你对结果的信任度反而更低。
  2. 诊断显示病灶不在内核。8 个维度的发现没有一条指向“地基错了”：分层、注册表、PIT、原子写、安全闸都是对的。问题全部是边缘漂移（复制后分叉）、堆积（死重存储）、和断线（动线/契约缺失）——这三类病的标准疗法都是定向手术，不是器官移植。
  3. 单人项目承受不起重写的真空期。重写期间平台不可用或半可用，而你的研究是连续进行的。路线图的每个阶段结束时平台都比之前更好用、且可随时停在任何阶段——这是渐进路线对单人研究者的决定性优势。

如果一定要给“重构”划出值得做的范围，就是阶段 2 的两项定向手术：共享交易内核与存储统一——它们是真正意义上的结构性重构，但被限定在两个明确边界内，且有阶段 1 先建好的测试网兜底。
